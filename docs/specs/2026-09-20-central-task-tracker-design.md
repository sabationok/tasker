# Central Task Tracker — Design Spec

> Status: draft for review · Date: 2026-09-20 · Author: vitalii + Claude
> Classification: architectural (new standalone subsystem)

## 1. Goal

A **central, standalone local tool** that can open *any* project by path, read that
project's task data + audit READMEs, and present a graphical tracker (in the style of the
audit artifact) served **locally**. Task state lives in files **inside the target project's
repo**, so it is shared and versioned via git (not per-browser localStorage). Humans and
local agents share one source of truth; each can mark which tasks a person will do vs. which
are handed to an agent.

The long-term north star adds an **MCP layer** so local agents pull tasks programmatically
(`next_agent_task` → work → open PR → mark `done`). That is explicitly **later**, not now.

## 2. Scope

**Iteration 1 (build now):**
1. The **task files** in the target repo (`mia-erp-server` first).
2. The **local graphical tracker** (Next.js) over those files, in a **separate central repo**.
3. A **generator script** that (re)builds the task catalog from the project's READMEs / `FABLE_BACKLOG.md`.

**Out of scope for iteration 1** (captured in §9 roadmap): the MCP server, PR automation,
multi-project switching in the UI, authentication, remote hosting, Jira/Trello sync.

## 3. Architecture

Two clearly separated concerns:

- **The tool** — a standalone repo (e.g. `~/projects/tasker`). Central; not tied to
  any one project. Points at a target project via config/env (`PROJECT_PATH`). Contains the
  Next.js app + the generator script. Reusable across projects.
  **Stack:** Next.js (App Router) + TypeScript, **pnpm**, **Node 20+**.
- **The data** — lives in each target project under `tasks/`. The tool reads/writes it; git
  versions it. Regenerating the catalog never touches progress.

```
~/projects/tasker/            # the tool (central, standalone)
├── app/                                # Next.js (App Router)
│   ├── page.tsx                        # the board
│   └── api/tasks/route.ts              # GET merged catalog+state
│   └── api/tasks/[id]/route.ts         # PATCH one item's state
├── lib/                                # catalog+state readers, merge, atomic write
├── scripts/build-tasks.mjs             # generator (reads a project → catalog.jsonl)
└── tracker.config.(json|ts)           # { projectPath }

<target project>/tasks/                 # the data (per project, in repo)
├── catalog.jsonl                       # GENERATED — what tasks exist
└── state.json                          # OWNED by humans/agents/tracker — progress
```

## 4. Data model

### 4.1 `tasks/catalog.jsonl` (generated, one JSON object per line)

Rarely changes; regenerated by the script. Three record `level`s.

Module header (carries the P1/P2/P3 counts and domain for the board):
```json
{"id":"M:payments","level":"module","module":"payments","domain":"Finance","p1":5,"p2":5,"p3":1,"refs":["src/payments/README.md"]}
```
Module P1 task (child of a module header):
```json
{"id":"M:payments#1","level":"module-p1","module":"payments","parent":"M:payments","priority":"P1","title":"confirm/finalize reconciliation is not atomic and not idempotent","fix":"Load the payment with runWithIn(trManager) and a pessimistic write lock …","refs":["src/payments/README.md"]}
```
Systemic root cause:
```json
{"id":"S1","level":"systemic","priority":"P1","title":"Soft delete broken app-wide","fix":"Switch shared date decorators to @DeleteDateColumn …","affects":["shared","customers"],"refs":["docs/FABLE_BACKLOG.md"]}
```
Security-critical:
```json
{"id":"SEC7","level":"security","priority":"P1","title":"statistics — SQL injection via interpolated jsonb_set","modules":["statistics"],"refs":["docs/FABLE_BACKLOG.md"]}
```

**ID scheme** (stable, reused from the current tracker): `S1..S12`, `SEC1..SEC15`,
`M:<module>` (header), `M:<module>#<n>` (P1 item, 0-based). IDs must be stable across
regeneration so state never orphans — derived from module name + P1 order in the README.

### 4.2 `tasks/state.json` (owned by humans/agents/tracker)

```json
{
  "version": 1,
  "updatedAt": "2026-09-20T10:00:00Z",
  "items": {
    "M:payments#1": { "owner": "me",    "status": "doing",  "comment": "start after S2", "updatedAt": "…" },
    "S1":           { "owner": "fable", "status": "review", "comment": "PR #123",        "updatedAt": "…" }
  }
}
```
- `owner ∈ {me, claude, fable, null}` — who does it.
- `status ∈ {todo, doing, blocked, review, done}` — the selectable per-task state; `done`
  counts as complete; `blocked` = waiting on a dependency (e.g. a systemic fix), shown
  distinctly and excluded from "in progress".
- `comment` — free text; doubles as the "definition of done" / PR link / hand-off note.
- Only ids present in `state.json` carry progress; absent ids default to `{owner:null,status:"todo"}`.

## 5. Generator (`scripts/build-tasks.mjs`)

`node scripts/build-tasks.mjs --project <path>`:
1. Reads `<project>/src/*/README.md` — parses `### [P1] <title>` blocks + their `**Fix:**`
   line (the existing extractor logic, ported to Node). Reads `FABLE_BACKLOG.md` for the
   S/SEC catalog and per-module P1/P2/P3 counts + domains.
2. Writes `<project>/tasks/catalog.jsonl` (stable id + line order → clean diffs).
3. **Preserves `state.json`**: never overwrites it; if it doesn't exist, creates an empty
   one. Emits a warning listing any `state.json` ids no longer present in the catalog
   (orphans) so they can be pruned deliberately.

Rationale for two files: regenerating the catalog after READMEs change must not wipe
progress; jsonl gives one-task-per-line git diffs and fewer merge conflicts when a human and
an agent edit concurrently.

## 6. Tracker app (Next.js)

Carries over the current artifact's design and behavior, swapping localStorage for the repo
files via API:

- **Board**: groups Systemic → Security → modules (by domain), modules expand to show their
  P1 tasks with title + `Fix`. Reuses the audit palette, both light/dark themes, the
  "what do the codes mean?" legend, and the UK/EN toggle (UI translated; task text stays
  English).
- **Per task**: `owner` pill (me/claude/fable cycle) — assignable on **all levels** (systemic,
  security, and module P1 tasks), a `status` selector (todo→doing→blocked→review→done), and a
  `comment` field. All persist to `state.json` via the API.
- **Summary**: progress ring + status/ownership breakdown, computed over P1 leaves + S + SEC.
- **Filters/sort**: by status, owner, priority, leverage (unchanged from current tracker).
- **Delegate queues**: "Copy Claude/Fable queue" and "Export" generate markdown from open,
  owner-assigned items (with `Fix` text) — the same hand-off affordance as today.

### 6.1 API
- `GET /api/tasks` → catalog (from `catalog.jsonl`) merged with `state.json`, ready to render.
- `PATCH /api/tasks/:id` → update `{owner?, status?, comment?}` for one id; writes `state.json`
  **atomically** (temp file + rename); stamps `updatedAt`. Optimistic concurrency: request
  carries the item's `updatedAt`; a mismatch returns 409 so a stale tab can't clobber (thin
  guard; single local user, but cheap to include).
- Catalog regeneration is CLI-only in iteration 1 (a `POST /api/regenerate` is a later nicety).

## 7. How agents consume it

**Now (no MCP):** because tasks are plain files in the repo, a local agent (Claude Code,
Fable) already reads `tasks/catalog.jsonl` + `tasks/state.json`, filters `owner ∈ {agent-ish}`
+ `status:todo`, does the work, and writes back `status:"review"` with the PR link in
`comment`. A short `tasks/AGENTS.md` convention documents this contract.

**Later (MCP, §9):** the same store is wrapped by an MCP server exposing
`list_tasks(filter)`, `assign_task(id, owner)`, `next_agent_task()`, `complete_task(id, pr)`.
The tool becomes the single interface; the file schema does not change.

## 8. Error handling & edge cases
- Atomic writes (temp + rename) so a crash never leaves a half-written `state.json`.
- Missing `tasks/` dir → generator creates it; tracker shows an empty state with a "run
  generator" hint.
- Orphaned state ids (task removed from catalog) → surfaced, not silently dropped.
- Malformed `catalog.jsonl` line → skipped with a console warning, rest still loads.

## 9. Iteration roadmap
- **it1 (this spec):** task files + local Next.js tracker + generator. Single project via config.
- **it2:** MCP server over the same store (list/assign/next/complete) + documented agent loop.
- **it3:** multi-project switching in the UI; optional `POST /api/regenerate`; PR-status ingestion.
- **it4 (optional):** one-way mirror/sync to Jira or Trello for stakeholders.
